# Rules for Claude in dashboard/

Also read `../CLAUDE.md`: the procedure, the dialogue and the cross-effects apply here. "The user" is whoever is giving the instructions.

## Questions to ask, by scenario

Ask only what the files can't tell you. Show the user the answer you've assumed if the request already implies it.

- **2. Text.** Which passage (quote it back). What should it say instead; if the user has no wording, say "I'll draft it and show you". Why (so the change log says so). Should grammar fixes elsewhere in the same passage be made too (default: yes).
- **3. New indicator or design.** Indicator: which measure; which table and column it comes from; where it goes (a tile, a chart, the map, the district card); compared with what (groups, places, years); what the denominator is. Design: what exactly changes, where, and what it should look like (ask for a screenshot or an example). A picture: what it should show and what is wrong with the one there; show the new one before it goes on the page. Then say which files the change touches before starting.
- **4. Under construction.** Freeze (site stays as it is) or hide (holding page)? For how long, and who restores it?
- **5. Something failed.** What the user sees, on which part of the page, in which browser, since when, and what changed last (check `CHANGELOG.md` and the git history yourself first).
- **6. Slow.** Where it's slow (first load, the map, a chart), on what device and connection. Then measure before proposing anything.
- **7. GitHub or Netlify.** What was done last and what the screen says (ask for the exact error text or a screenshot). Read the Netlify deploy log if the problem is publishing.
- **10. Restore.** Restore what (one file, or the whole page) and to when (a date, or "the last version that worked"). Show the candidate commit before restoring.

## Do

- Keep the structure: `index.html` (words and drawings), `charts.js` (the menu and the drawing of charts and map), `styles.css` (looks), `data/` (generated numbers), `resources/` (libraries and fonts we didn't write).
- Keep every number on the page coming from `data/data.json`: `data-fill` tags in the text, the chart functions in `charts.js`.
- Keep the code readable: plain-language comments, named sections, one function per chart, settings at the top of the file. Part one of `charts.js` and parts A and B of `styles.css` are copied unchanged from the Youth Justice Dashboard: change them there and here together, or not at all.
- After any change, open the page in a browser at desktop and phone width, every tab, and fix anything that overflows, overlaps or errors before reporting back. Show screenshots for anything visual.
- Show the old and new text side by side for any wording change before committing.
- Whenever `data/data.json` changes, re-read every opening panel, takeaway and "What we see" claim against the new numbers (the list is in the comment at the top of `index.html`) and report which no longer hold.
- Check any new color for color-blind readers before using it (the colors at the top of `styles.css` have already been checked).
- For a failure (scenario 5), name a cause only with evidence: the error text and what triggers it. Propose the smallest fix. If you can't reach confidence, say so instead of guessing.
- For slowness (scenario 6), measure first and report numbers; propose fixes ranked by gain and risk; change nothing without approval.
- Add a line to `CHANGELOG.md` (date, who, what, why) as part of every change, before committing, naming who asked.
- Stop and ask the user when a request is ambiguous or touches something these rules don't cover. Say what you found and the options; wait for the answer.

## Don't

- Don't edit anything in `data/` by hand. It is generated by `../update_data_here/build_data.py`.
- Don't add libraries, folders, build tools or anything loaded from an outside site (fonts, scripts, map tiles). Everything the page needs loads from this folder. (Links a reader can click, such as "Take action", are fine.)
- Don't define a color or font anywhere except the top of `styles.css`.
- Don't change what the dashboard says without being asked: which measures, which charts, which groups, which denominators. "Sent home" always means suspended out of school at least once, out of every 100 students enrolled in October.
- Don't put a chart's point in its title: the title says what is measured; the point goes in the orange circle on the chart and/or in "What we see".
- Don't redraw, add, remove or swap a picture without asking the user, and don't copy anything from `../archive/` without asking.
- Don't rewrite the text beyond what was asked; it belongs to the user and their team. Grammar fixes yes (unless told not to); new meaning no.
- Don't push, revert or restore anything in git without the user's explicit go-ahead for that specific action.
